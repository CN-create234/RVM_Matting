# RVM 算法代码分析：分割原理与使用场景

## 1. 分析对象与结论摘要

本项目采用 **RVM（Robust Video Matting）MobileNetV3 FP16 ONNX 模型**，模型文件为 `rvm_mobilenetv3_fp16.onnx`。核心推理代码主要位于：

- `RVM_LocalFiles.py`：对 PNG 序列进行离线批量抠像；
- `RVM_Livefeed.py`：通过 FFmpeg 从 DeckLink 采集视频并逐帧推理；
- `Composure.py`：完整的 EXR 重命名、EXR→PNG、RVM 推理、背景合成和 MP4 生成流程；
- `Compositing_w_bg.py`：将预测前景与指定背景合成；
- `Compositing_wo_bg.py`：将前景与 Alpha 组合成透明 RGBA 图像；
- `LocalStreaming.py`：将前景流和遮罩流通过 NDI 发送。

核心结论如下：

1. 当前算法本质是**人像视频抠像（human video matting）**，不是一般意义上的多类别语义分割。
2. 模型对每帧同时输出三通道前景 `fgr` 和单通道透明度 `pha`，能够表达头发、运动模糊、半透明边缘等软边界。
3. 模型通过 4 组循环状态在相邻帧之间传递记忆，因此相较逐帧分割具有更好的时间稳定性。
4. 当前项目已形成“UE 输出/采集卡输入 → RVM 抠像 → 虚实合成/透明素材 → 视频或 NDI 输出”的基本链路，适合实时人像抠像、虚拟制作、直播换背景等场景。
5. 当前实现能够验证算法，但仍存在固定路径、逐帧磁盘写入、GPU/CPU 频繁传输、镜头切换不重置状态等工程瓶颈。

## 2. “分割”与“抠像”的区别

传统二值分割为每个像素判断“前景或背景”，输出通常为 0/1 掩码。RVM 解决的是更细粒度的图像抠像问题，其成像模型为：

\[
I = \alpha F + (1-\alpha)B
\]

其中：

- \(I\)：原始图像；
- \(F\)：真实前景颜色；
- \(B\)：背景颜色；
- \(\alpha\)：每个像素的前景不透明度，取值范围为 0～1。

二值分割只能产生硬边界，而 Alpha Matting 可以让边界像素取 0～1 之间的连续值。因此，RVM 更适合处理头发丝、衣物边缘、快速运动产生的模糊以及部分透明区域。项目代码将 `pha` 转换为 8 位灰度 Alpha，并使用以下公式完成背景替换：

\[
C = F\alpha + B(1-\alpha)
\]

这与 `Composure.py` 和 `Compositing_w_bg.py` 中的实现一致。

## 3. RVM 的分割/抠像原理

### 3.1 无需绿幕和 Trimap 的端到端预测

RVM 仅需要普通 RGB 视频帧，不需要额外输入绿幕、背景图、Trimap 或人工标注。网络直接从当前帧和历史循环状态预测：

- `fgr`：去除背景污染后的 RGB 前景；
- `pha`：单通道 Alpha Matte；
- `r1o`～`r4o`：供下一帧使用的 4 级循环状态。

因此它可以在未知背景下工作，但预训练模型的主要语义目标是“人”。它不是任意物体抠像模型，也不会输出人体部位类别。

### 3.2 MobileNetV3 编码器提取多尺度特征

当前模型名中的 `mobilenetv3` 表明其采用轻量级 MobileNetV3-Large 作为特征编码器。编码器逐级降低空间分辨率并提取不同尺度特征：浅层特征保留边缘和纹理，深层特征用于判断人体语义及整体轮廓。相比 ResNet50 版本，MobileNetV3 版本更偏向实时性和部署效率，适合当前采集卡、直播和 UE 合成链路。

### 3.3 循环解码器利用时间信息

RVM 的关键不只是单帧卷积网络，而是带有循环记忆的解码器。模型内部在多个尺度上使用 ConvGRU，并将上一帧产生的 4 组状态作为下一帧输入：

```text
当前帧 src(t) + 上一时刻状态 r1～r4(t-1)
                   ↓
          编码器 + 循环解码器
                   ↓
        fgr(t)、pha(t)、r1～r4(t)
```

项目中 `rec` 初始为 4 个全零张量；每次 `sess.run()` 后，`outs[2:6]` 会覆盖旧的 `rec`，再送入下一帧。这样可以利用人物过去的位置、轮廓和运动趋势，减少逐帧模型常见的边缘闪烁、局部漏检和时序跳变。

循环状态也带来两个约束：

- 视频帧必须按时间顺序处理，不能随意打乱；
- 新视频、硬切镜头或不连续片段开始时应重置状态，否则上一个镜头的记忆可能污染新镜头。

### 3.4 两阶段高分辨率处理与 `downsample_ratio`

RVM 先在降采样图像上完成主要语义和时序推理，再结合高分辨率输入细化输出。`downsample_ratio` 控制低分辨率分支的尺寸，是速度、显存和细节质量之间的重要权衡。

当前所有核心脚本均固定使用 `0.25`：

- 对 1920×1080 输入，内部低分辨率约为 480×270，属于官方建议范围；
- 对 1280×720 全身画面，0.25 可能偏低，细小手脚、远景人物和快速运动更容易丢失；
- 提高该值通常能保留更多全身细节，但会增加推理开销；数值也并非越大越好，应按分辨率和人物在画面中的占比测试。

官方参考建议为：720p 人像约 0.375、720p 全身约 0.6；1080p 人像约 0.25、1080p 全身约 0.4。实际项目仍应以目标硬件上的质量和帧率测试为准。

### 3.5 高分辨率细化

原始 RVM 网络由特征编码器、循环解码器和高分辨率细化模块组成。低分辨率分支负责稳定地识别人和估计主体 Alpha，高分辨率信息用于恢复边缘细节。因此，模型能够以较低计算成本处理 HD/4K 视频，同时避免单纯把低分辨率遮罩放大造成的锯齿和细节损失。

## 4. 当前代码的数据流

### 4.1 离线完整流程

`Composure.py` 的主流程如下：

```text
UE 视频 EXR 序列 ─→ 重命名 ─→ Gamma 转换为 PNG ─→ RVM
                                                     ├─→ *_fgr.png
                                                     └─→ *_alpha.png
UE CG 背景 EXR 序列 ─→ 重命名 ─→ Gamma 转换为 PNG ────────┐
                                                            ↓
                                      Alpha 合成 ─→ PNG 序列 ─→ MP4
```

各阶段职责为：

1. `rename_exr_sequence()`：将 EXR 序列整理为连续的四位编号；
2. `transform_exr_to_png()`：读取线性 EXR，执行约 2.2 Gamma 变换并输出 8 位 PNG；
3. `run_rvm_batch()`：进行 RGB/BGR 转换、归一化、NCHW 排列和 ONNX 推理；
4. `composite_rvm_with_background()`：根据 Alpha 混合预测前景与 CG 背景；
5. `png_sequence_to_mp4()`：将合成 PNG 序列编码为 MP4。

### 4.2 实时流程

`RVM_Livefeed.py` 使用 FFmpeg 的 DeckLink 输入获得 1280×720 BGR24 原始帧，随后逐帧执行 RVM。现有脚本把每帧 `fgr` 和 `alpha` 写入 `DebugOutputs`；`LocalStreaming.py` 再读取这些文件并通过两个 NDI Sender 发送前景和遮罩。

这条链路在功能上可验证实时输入和 NDI 对接，但当前并非真正的低延迟流式处理，因为中间存在大量 PNG 磁盘读写和固定帧间 `sleep`。生产版本应将推理结果直接交给 NDI/视频编码器或 UE 接收端。

### 4.3 ONNX 输入输出

根据当前脚本与官方 ONNX 接口，模型结构为：

| 类型 | 名称 | 含义 |
|---|---|---|
| 输入 | `src` | `[1,3,H,W]` FP16 RGB，范围 0～1 |
| 输入 | `r1i`～`r4i` | 4 组上一帧循环状态，首帧为 `[1,1,1,1]` 零张量 |
| 输入 | `downsample_ratio` | `[1]` FP32 缩放系数 |
| 输出 | `fgr` | `[1,3,H,W]` 前景 RGB，范围 0～1 |
| 输出 | `pha` | `[1,1,H,W]` Alpha，范围 0～1 |
| 输出 | `r1o`～`r4o` | 4 组更新后的循环状态 |

当前代码按输入和输出的数组顺序绑定张量。对官方模型通常有效，但按明确名称绑定会更稳健，可避免模型重新导出后接口顺序变化导致静默错误。

## 5. 适用场景

### 5.1 很适合的场景

- **直播与视频会议换背景**：无需绿幕，能实时产生人物 Alpha；
- **虚拟制作与 UE 合成**：真人前景可与 Unreal Engine 的 CG 场景融合；
- **采集卡现场抠像**：当前 DeckLink + FFmpeg 输入已具备原型基础；
- **短视频和后期批处理**：适合对连续人物视频输出透明素材或替换背景；
- **AR/互动展示**：可把人物作为独立图层叠加到虚拟内容中；
- **NDI 广播链路**：可分别发送前景和 Matte，交给下游导播或合成系统处理；
- **数字人/远程演示**：真实人物与虚拟场景结合，并保持帧间边缘稳定。

### 5.2 有条件适用的场景

- **多人画面**：模型通常能提取画面中的人，但小人物、拥挤遮挡和人物相互交叉会降低质量；
- **全身及远景人物**：需要提高 `downsample_ratio`，并评估实时帧率；
- **复杂发丝、快速动作和运动模糊**：RVM 比硬分割更有优势，但强模糊、低照度或压缩噪声仍会产生残影；
- **长时间直播**：需要避免丢帧造成时间状态错位，并对镜头切换执行状态重置；
- **绿幕现场**：RVM 可使用，但若现场绿幕和灯光质量高，传统色键可能更可控、更容易人工调参。

### 5.3 不适合或风险较高的场景

- **任意物体类别分割**：该预训练模型针对人物，不能可靠抠出商品、车辆、动物或建筑；
- **需要类别标签的任务**：它不会区分头、手、衣服等人体部位；
- **单帧高精度商业抠图**：循环优势无法充分发挥，且专业静态抠图可能需要交互式 Trimap 或人工修边；
- **严重遮挡、极暗、强逆光、人物与背景纹理高度相似的镜头**：容易出现漏抠、背景残留和边缘污染；
- **镜面、玻璃、透明纱、细密网格等复杂透明结构**：Alpha 估计可能不稳定；
- **对像素级可验证精度有硬性要求的安全、医疗或工业检测**：RVM 的目标是视觉合成，不是可解释的测量或检测模型。

## 6. 当前实现的优点

1. **模型选择合理**：MobileNetV3 FP16 兼顾质量、速度和模型体积，符合实时合成方向。
2. **正确保留了循环状态**：离线和实时脚本都把 4 组状态回传给下一帧，使用了 RVM 最重要的时间信息。
3. **输出完整**：同时保存 `fgr` 和 `alpha`，比只输出二值 Mask 更适合后续合成。
4. **已有端到端验证链路**：从 UE EXR 素材到 MP4 成片的步骤已经贯通。
5. **具备多种输出形态**：可输出透明 RGBA、指定背景合成结果以及 NDI 前景/遮罩流。

## 7. 当前代码的主要问题与改进建议

### 7.1 高优先级

1. **镜头切换时重置 `rec`**  
   当前一个目录只初始化一次循环状态。如果文件序列包含多个镜头，或输入中发生硬切，应将 4 组状态重新设为零，避免前一镜头残影影响后一镜头。

2. **实时链路去除逐帧 PNG 磁盘往返**  
   `RVM_Livefeed.py` 每帧写文件，`LocalStreaming.py` 再读文件，会显著增加延迟并限制帧率。应在内存中直接构造 NDI 帧或推送给编码器。

3. **使用 ONNX Runtime I/O Binding**  
   当前 `sess.run()` 会让循环状态每帧在 GPU 与 CPU 之间往返。将循环状态常驻 GPU，只把最终 `fgr`/`pha` 传回 CPU，可明显减少无效拷贝。

4. **检查实际执行 Provider**  
   离线代码虽然声明 CUDA 后接 CPU，但应打印 `sess.get_providers()` 并在 CUDA 不可用时明确告警。实时脚本只声明 CUDA，缺少可读的失败诊断。

5. **增加 Alpha 裁剪**  
   在乘以 255 并转为 `uint8` 前应执行 `np.clip(pha, 0, 1)`，避免极少量越界预测在无符号转换时产生异常值。

### 7.2 中优先级

1. 把模型路径、输入目录、输出目录、分辨率、帧率、Provider 和 `downsample_ratio` 改为命令行参数或配置文件；
2. 按输入名明确绑定 `src/r1i/r2i/r3i/r4i/downsample_ratio`，按输出名读取结果；
3. 对输入帧尺寸、色彩空间、数据类型和推理输出形状增加断言；
4. 对文件序列使用自然排序或验证连续编号，避免普通字符串排序造成帧顺序错误；
5. 检查 `cv2.imwrite()`、视频写入器和 FFmpeg 子进程返回状态，避免静默失败；
6. 不要完全丢弃 FFmpeg 标准错误，应保存日志以诊断采集格式、掉帧和设备问题；
7. 复用输入/输出缓冲区，并把解码、推理、合成和发送拆成流水线，减少串行等待；
8. 对直播中的硬切、长时间无人物、分辨率变化和输入中断建立明确的状态机。

### 7.3 质量优化方向

- 对 720p 全身、1080p 半身、多人和快速运动分别标定 `downsample_ratio`；
- 用项目中的困难样例建立固定测试集，至少记录 SAD/MSE、边缘质量、时序抖动和实际端到端延迟；
- 对白色衣物、雪景、逆光、发丝、运动模糊和相似背景重点做回归测试；
- 如果 MobileNetV3 的质量不足且硬件余量足够，可比较 RVM ResNet50 版本；
- 如果重点是单帧精修而非实时视频，应考虑带 Trimap/交互信息的高精度 Matting 方案。

## 8. 项目定位建议

当前项目最合适的定位是：

> 基于 RVM 的实时/离线人像视频抠像与 Unreal Engine 虚实合成原型系统。

其技术优势是无需绿幕、具有时间记忆、能够输出软 Alpha，并可衔接采集卡、UE、视频文件和 NDI。后续开发的重点不应只是继续增加离线脚本，而应转向：实时内存流水线、状态管理、参数化配置、质量基准和端到端延迟优化。
